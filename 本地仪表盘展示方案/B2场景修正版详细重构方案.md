# B2 场景修正版详细重构方案

## 1. 目标与约束

### 目标
- 承认“仅合约无现货”客观存在
- 不再强行单榜混排
- 保留覆盖率，同时保住结果可信度
- 在不使用反代、不购买 VPS、必须大陆直连的约束下，给出可持续的本地仪表盘重构方案

### 硬约束
- 绝不反代
- 绝不买 VPS
- 必须大陆直连

---

## 2. 问题背景

以 `B2USDT` 为例：

- `B2` 在币安是**只有合约（Futures），没有现货（Spot）**的币种
- `data-api.binance.vision` 只能拉现货公共数据
- 因此对 `B2USDT` 请求现货 K 线会失败
- 这类币不能依赖“合约 -> 现货”的映射逻辑解决

需要区分两类标的：

### 2.1 真正仅合约、无现货
示例：
- `B2USDT`
- 部分新币、特殊合约币

特点：
- 无法从 `Binance Vision Spot` 获取 K 线
- 必须走二级来源，或者进入未覆盖列表

### 2.2 合约代码与现货代码不一致，但本质上有现货
示例：
- `1000PEPEUSDT -> PEPEUSDT`
- `1000SHIBUSDT -> SHIBUSDT`
- `1MBABYDOGEUSDT -> BABYDOGEUSDT`

特点：
- 通过映射后，仍可进入主榜
- 不应与真正“仅合约无现货”的情况混为一谈

## 4. 三层榜单设计

### 4.1 主榜 `Primary Board`
适用对象：
- 合约能映射到币安现货
- `Binance Vision` 能拉到 `1h` K 线

示例：
- `BTCUSDT`
- `PEPEUSDT`（对应合约 `1000PEPEUSDT`）

特点：
- 口径最统一
- 可以做正式排序
- 可以触发 `ratio` 告警

### 4.2 扩展榜 `Futures-Only Board`
适用对象：
- `B2USDT` 这种只有合约、没有现货
- 主源 `Vision` 无法覆盖
- 二级源 `Gate Futures` 可以给到 `1h` K 线

特点：
- 可以显示
- 可以单独排序
- **不能和主榜混排**

### 4.3 未覆盖 `Uncovered`
适用对象：
- 无现货
- 二级源也失败
- 或映射关系不确定

特点：
- 只展示状态
- 不参与排行
- 不参与告警

## 5. 标的分类状态机

```text
合约 symbol
   │
   ▼
是否可映射 spot_symbol?
   ├─ 是 ─► 试拉 Binance Vision 1h
   │          ├─ 成功 ─► PRIMARY
   │          └─ 失败 ─► 再试 Gate Futures
   │                     ├─ 成功 ─► SECONDARY
   │                     └─ 失败 ─► UNCOVERED
   │
   └─ 否 ─► 试拉 Gate Futures
              ├─ 成功 ─► FUTURES_ONLY
              └─ 失败 ─► UNCOVERED
```

### 5.1 对 `B2USDT` 的结果
- 无 `spot_symbol`
- `Vision` 跳过
- `Gate Futures` 成功
- 进入 `Futures-Only Board`

### 5.2 对 `1000PEPEUSDT` 的结果
- `spot_symbol = PEPEUSDT`
- `Vision` 成功
- 进入 `Primary Board`

## 6. 核心设计原则

### 6.1 不再只传一个 `symbol`
必须拆成：
- `contract_symbol`
- `spot_symbol`

原因：
- 合约身份与现货身份不能混用
- `1000PEPEUSDT` 这类前缀合约必须保留原始合约身份
- 排名、跳转、OI/Vol 合并都应基于 `contract_symbol`
- `Vision` 查询则基于 `spot_symbol`

### 6.2 只允许同一可比组内排序
通过 `comparability_group` 限定：
- `binance_vision_spot_1h`
- `gate_futures_1h`

规则：
- 同组内可排序
- 跨组绝不混排

### 6.3 Coinglass 只做指标补充，不做系统单点入口
Coinglass 作用应缩减为：
- 提供 `OI`
- 提供 `24h Vol`
- 辅助发现新增合约

但不能决定：
- 主扫描 universe 是否存在
- 页面是否清空
- 主榜是否归零

## 8. 排名规则

### 8.1 主榜排序
只对 `comparability_group = binance_vision_spot_1h` 排序：

```text
1. duration_bars desc
2. bbw asc
3. oi_vol_ratio desc
```

### 8.2 扩展榜排序
只对 `comparability_group = gate_futures_1h` 排序：

```text
1. duration_bars desc
2. bbw asc
3. oi_vol_ratio desc
```

### 8.3 禁止规则
- `primary` 与 `futures_only` **绝不混排**
- `uncovered` 不排序
- 不允许把不同来源的 `duration`、`bbw`、`ratio` 直接合并进同一个排行榜

## 9. 缓存设计

建议从单个 `sideways_history.json` 升级为 4 类缓存。

### 9.1 `symbol_registry.json`
维护标的身份与映射：

```json
{
  "B2USDT": {
    "contract_symbol": "B2USDT",
    "spot_symbol": null,
    "mapping_status": "no_spot",
    "board_type": "futures_only"
  },
  "1000PEPEUSDT": {
    "contract_symbol": "1000PEPEUSDT",
    "spot_symbol": "PEPEUSDT",
    "mapping_status": "mapped",
    "board_type": "primary"
  }
}
```

### 9.2 `metrics_snapshot.json`
缓存 `Coinglass` 指标：

```json
{
  "timestamp": 1710000000,
  "items": {
    "B2USDT": { "oi_value": 123, "vol_value": 456 },
    "1000PEPEUSDT": { "oi_value": 789, "vol_value": 999 }
  }
}
```

作用：
- `Coinglass` 失败时保留上次值
- 防止失败即全清空

### 9.3 `kline_cache.json`
缓存各来源的最近 K 线摘要：

```json
{
  "binance_vision_spot_1h:PEPEUSDT": {
    "last_close_time": 1710000000,
    "duration_bars": 8,
    "bbw": 0.0312,
    "price": 0.0000123
  },
  "gate_futures_1h:B2USDT": {
    "last_close_time": 1710000000,
    "duration_bars": 6,
    "bbw": 0.0251,
    "price": 0.7136
  }
}
```

### 9.4 `board_snapshot.json`
前端直接消费：

```json
{
  "timestamp": "14:05:00",
  "primary_board": [],
  "futures_only_board": [],
  "uncovered": []
}
```

## 10. 调度建议

```text
每 5 分钟
  └─ 推送缓存、刷新状态，不做全量历史重拉

每 10~20 分钟
  └─ 刷新 Coinglass OI/Vol

每逢整点 + 1 分钟
  ├─ 跑 Primary Board K线计算
  ├─ 跑 Futures-Only Board K线计算
  └─ 重新生成 board_snapshot

每 6~12 小时
  └─ 刷新 symbol_registry
```

### 调度原则
- `1h` 策略应以收线为主
- `Coinglass` 不需要和 K 线同频
- 页面推送频率可以高，但指标重算频率不必高

## 13. 与现有实现对应的关键改造点

### 13.1 `contract_to_spot` 需要升级
建议：
- 长前缀优先匹配
- 不只返回字符串，应返回结构化映射信息
- 标记 `mapped / no_spot / suspect`

### 13.2 Coinglass 解析阶段不能破坏原始合约身份
当前做法会直接修改 symbol 语义，后续应避免。
应保留：
- 原始 `contract_symbol`
- 目标 `spot_symbol`
- 显式映射状态

### 13.3 输出层必须带分层字段
输出中必须增加：
- `contract_symbol`
- `spot_symbol`
- `board_type`
- `coverage_level`
- `comparability_group`
- `kline_source`
- `metric_source`
- `alert_eligible`

### 13.4 不再把不同来源直接塞进同一个 `results`
改为：
- `primary_results`
- `futures_only_results`
- `uncovered_results`

之后分别排序、分别渲染、分别推送。

---

## 14. 最终结论

在“绝不反代、绝不买 VPS、必须大陆直连”的约束下，**最合理的重构方向不是追求单源全覆盖，而是做“主榜 + 扩展榜 + 未覆盖”的分层架构**：

- 主榜只服务“可映射现货”的合约
- `B2` 这类真仅合约币进入扩展榜
- `Coinglass` 从单点故障改成低频补充指标源
- 所有排序只在同一 `comparability_group` 内发生

一句话总结：

> 主榜保证可信度，扩展榜保证覆盖率，未覆盖列表保证系统诚实性。
